# Decisions

The decisions behind the gateway contract, each with its evidence. [spec.md](spec.md) is normative for
behaviour.

The table format, and the rule for a decision that changes the contract, are in
[platform decisions](../platform/decisions.md).

| 1 | Supported runtime versions | Built, tested and released on **Bun 1.4.3**; the contract states **Bun ≥ 1.4.3**. The 1.2 line was measured (1.2.0 and 1.2.23): it does not expose the early answer during an upload, does not cancel the body producer, its `ws` client cannot observe an upstream handshake refusal, and it refuses the caller upgrade with gateway headers. | §4 | resolved | [runtime.md](runtime.md), `test/network/transport.test.ts` |
| 2 | Upload and response commitment boundaries | The observable events are the **end of the request stream**, the **final response headers** and the **first body byte**. | 3 | Refusal of an upstream WebSocket handshake | Reported separately from a network failure: the caller gets `502 bad_gateway`, the upstream body is not forwarded, the refusal status is logged, and the connection slot is released. | — | resolved | `test/network/transport.test.ts` |
| 4 | Connection establishment during an upload | No extra ceiling. The upload is governed only by the idle `bodyMs` budget, so a client that keeps making progress is never cut off by a total budget. | 5 | The caller's `Authorization` header and the standard `Forwarded` header | The standard `forwarded` header is **removed** in both directions. | 6 | Header representation | Roles are a comma-separated list. A role containing a comma or control character is dropped from the header but kept in the access-service request. | 8 | Consuming the login transaction | Login state is single-use at four levels: the state cookie is deleted once the callback is processed; the callback state must match the cookie; the verifier and nonce bind the exchange to the login attempt; and the provider makes the authorization code single-use. | 9 | Decision-cache outage | Only explicit access-service decisions are cached, never a transport failure. | 10 | Live WebSocket authorization | Authorized at the handshake **and** revalidated every `GATEWAY_WS_REVALIDATE_INTERVAL_MS`. A revalidation that cannot run also closes the connection: the gateway must not keep a connection it cannot vouch for. | §10 | resolved | `src/domains/websockets/bridge.test.ts`, `test/contract/websocket-revocation.test.ts` |
| 11 | Provisioning the signature verifier | The upstream gets the **derived** key, not the master secret, versioned by the signature version (`v3`). **Superseded** by decisions 40 and 57: `1.0` is asymmetric (`v5`) and the symmetric formats are removed. | §7.4 | superseded | `src/domains/forwarding/identity-signature.test.ts` |
| 12 | External host and response caching | The gateway neither caches responses nor adds cache headers. Upstream responses, including their cache headers, are forwarded as is: caching policy is not the gateway's. | — | resolved | `test/contract/endpoints.test.ts` |
| 13 | Replica topology and shared-state TLS | Replicas share sessions, rate limits and the decision cache through a shared server, whose TLS is verified with the deployment CA. Process caps (sessions, connections, buffers, exchanges) are per process, so several replicas multiply them. | — | resolved | [operations.md](operations.md), `src/runtime/env/` |
| 14 | Drain policy | While draining, readiness answers `503` with body `draining`, the listener stops accepting new work, WebSockets close with code 1001, and running exchanges are cancelled at the deadline. | — | resolved | `test/contract/lifecycle.test.ts` |
| 15 | Request host | The **effective host** is a trusted proxy's `x-forwarded-host`, else the `Host` header. It picks the route, is compared with the browser's origin, and is covered by the signature. The header from a non-trusted client is ignored, as is an implausible host value. The last list value is used, because an appending proxy writes its value last. | §7.3 | resolved | `test/contract/forwarding.test.ts` |
| 16 | Request metrics | Every gateway answer is counted, refusals included, with its matched route or `unmatched`. Labels are bounded (`other` for untracked methods and statuses), so neither clients nor upstreams can grow series without limit. Routes are capped at 500; the rest aggregate into `overflow`. | §12.1 | resolved | `test/contract/metrics.test.ts`, `src/observability/observability.test.ts` |
| 17 | Limit scopes | Four scopes: the deployment, the caller across routes, the caller on one route, and the authenticated caller on one route. An **address**-keyed scope cannot bound a flood spread over many addresses, nor separate two tenants behind one address. The deployment scope has no address; the principal scope is keyed by subject. | §9 | resolved | `src/domains/rate-limiting/rate-limiting.test.ts` |
| 18 | In-memory limiter table | Bounded at 10 000 keys. A key leaves only when its window ends, **never** to make room: evicting a live window would give that caller a fresh budget, letting an address-spraying caller reset its own counter. When the table is full, requests that do not fit share one window, so the flood is bounded by the same limit. | — | resolved | `src/domains/rate-limiting/rate-limiting.test.ts` |
| 19 | Concurrent exchanges | Bounded by `GATEWAY_MAX_CONCURRENT_REQUESTS`. A client that opens a request and never sends its body holds a connection until the idle upload budget expires (five minutes by default), which without a cap can exhaust the process. An exchange that does not fit gets `503 gateway_overloaded` instead of queueing. | §11.2 | resolved | `src/domains/proxying/exchange.test.ts` |
| 20 | Rate limits in production | Production refuses to start with every limit disabled, unless `GATEWAY_ALLOW_NO_RATE_LIMITS=true`. The limiter is the gateway's only flood protection, and a setting that looks active but is not is a security hole. | — | resolved | `src/runtime/env/env.test.ts` |
| 21 | Access revocation | Revocation latency is the decision-cache TTL (`GATEWAY_ACCESS_CACHE_TTL_MS`, 5 s by default), the knob to turn when revocation must be immediate. WebSocket revalidation asks the service again and skips the cache. | — | resolved | `src/domains/workspace-access/workspace-access.test.ts` |
| 22 | Production state | State is shared: sessions and replica state live in Redis or Postgres, unless the deployment explicitly declares a single node that keeps them in process (`GATEWAY_ALLOW_MEMORY_STATE=true`). A session in one replica's memory is unknown to the others, so callers are logged out at random; an in-memory limit applies per replica, so a flood is bounded only by the replica count. | §4 | resolved | `src/runtime/env/env.test.ts` |
| 23 | Per-route cross-site policy | A route property (`crossSite`). Cross-site navigations are allowed by default, because refusing them breaks every deep link; a route whose upstream changes state on a `GET` declares `strict` and is reachable only from its own site. The deployment policy (`GATEWAY_CSRF_STRICT`) applies to routes that declare none. | §8 | resolved | `src/domains/configuration/configuration.test.ts`, `test/contract/policies.test.ts` |
| 24 | The caller's `Authorization` header | Forwarded by default, since the upstream is a platform application the operator chose. A route that does not need it declares `forwardAuthorization: false`: the header is the caller's credential, and forwarding it puts the upstream in that credential's trust domain. The identity travels in the gateway headers and signature either way. | §7.1 | resolved | `src/domains/forwarding/headers.test.ts`, `test/contract/policies.test.ts` |
| 25 | Revocation latency | A route property (`accessCacheTtlMs`); the environment value is the default for routes that declare none. `0` asks the access service on every request, so revocation on that route is immediate. The cache key includes the route, so two routes' decisions never mix. | §6 | resolved | `src/domains/workspace-access/workspace-access.test.ts`, `test/contract/policies.test.ts` |
| 26 | WebSocket handshake header policy | The handshake is an upstream request and follows the HTTP header policy: gateway cookies never reach an upstream, the gateway writes the caller identity, and the caller's handshake headers are not forwarded. Before this release, the handshake copied the caller's headers and leaked the caller's session to the upstream. | §7.1, §10 | resolved | `src/domains/forwarding/headers.test.ts`, `test/contract/policies.test.ts` |
| 27 | Upstream TLS | The gateway verifies the upstream certificate with the deployment CA and presents the deployment certificate when asked. Certificate and private key go together: setting one without the other is refused at startup, because a setting that looks active but is not is a security hole. WebSocket upstreams use plain http, since the runtime's WebSocket client cannot speak TLS. | §11.1.2 | resolved | `src/runtime/env/env.test.ts`, `test/network/tls.test.ts` |
| 28 | Identity signature format | A **JWS** (RFC 7515), `HS256` with the derived key, with a **detached** payload: a canonical JSON object with named fields. The upstream rebuilds the payload from the request and identity headers, rebuilds the compact serialization around it, and verifies with a standard library. The `v3` format (a hex digest of a canonical JSON array) forced every upstream to implement a gateway-specific signature and comparison, which is easy to get wrong; the detached JWS makes verification one library call, and named fields cannot be confused. **Superseded** by decisions 40 and 57: `1.0` signs with `ES256` and the symmetric formats are removed. | §7.4 | superseded | `src/domains/forwarding/identity-signature.test.ts` |
| 29 | Cookie parsing | `Cookie` and `Set-Cookie` are parsed and rendered by a standards library. The gateway had two parsers of its own with slightly different rules, and both mishandled quoted values, values containing `=` and an `Expires` containing a comma (per RFC 6265). For a duplicated name, the first value wins, because browsers send the longest-path cookie first. | — | resolved | `src/domains/forwarding/cookies.test.ts` |
| 30 | Limiter window | The window **slides**: a caller's count is its requests in the last `windowMs`. A fixed window lets a caller spend the full budget at the end of one window and again at the start of the next, so twice the limit passes at once. Counts use at most 60 buckets, so per-caller state does not grow with traffic, and bucket boundaries are computable by every replica, so replicas count in the same buckets. | — | resolved | `src/domains/rate-limiting/window.test.ts`, `test/integration/redis-limiter.test.ts` |
| 31 | Shared-state client | The Redis client is the `redis` package, not the runtime's: the shared state must survive a runtime change, and the runtime client could not talk to a cluster or sentinel. The offline queue stays disabled: a command sent before connecting fails immediately, so the gateway denies the caller instead of piling up requests. The connection is established in the background, so a gateway that starts while the shared state is down stays up and becomes ready when the server answers. | — | resolved | `src/platform/redis/client.test.ts`, `test/integration/redis-sessions.test.ts` |
| 32 | Shared-state backend | Replica state lives in **Redis or Postgres**; the URL scheme picks the backend, and both hold the same three things under the same contract. The same test suite runs against both (`test/support/shared-state-conformance.ts`), and both are benchmarked side by side (`scripts/ops/benchmark.ts`). The deployment chooses; the gateway measures both so the choice is informed. | §4, §12.5, §12.6 | resolved | `test/integration/postgres-conformance.test.ts`, `test/integration/redis-conformance.test.ts`, [capacity.md](capacity.md) |
| 33 | Postgres atomicity | The two Redis scripts become two Postgres **functions**; a function call is a server transaction, the equivalent of a script. An advisory lock serializes checks of one key, so two replicas counting the same request at once count it once. The deployment counter is exact, and the replica test proves it with several processes. | — | resolved | `src/platform/postgres/schema.ts`, `test/integration/postgres-replicas.test.ts` |
| 34 | Postgres durability | The server does **not** wait for the disk (`GATEWAY_POSTGRES_SYNCHRONOUS_COMMIT=off`, the default). The shared state is a protection, not a ledger; the guarantee matches Redis without its append-only file. It is the difference between a millisecond and a tenth of one on every limiter transaction, and the limiter is on every request's path. | — | resolved | [capacity.md](capacity.md), `src/platform/postgres/client.ts` |
| 35 | Postgres row expiry | A Redis key expires by disappearing; a Postgres row's expiry is a column. The adapter sweeps expired rows, and the server never serves an expired row whatever the sweep did, because expiry is checked on read too. | — | resolved | `test/integration/postgres-conformance.test.ts` |
| 36 | Runtime version | The gateway **refuses to start** on a runtime older than **Bun 1.4.3**. The contract stated the version but nothing checked it: on the 1.2 line the gateway booted and then misbehaved (the upstream's early answer was not delivered, the body producer was not cancelled, an upstream WebSocket handshake refusal was unobservable, and the caller upgrade with gateway headers was refused). Those differences only show in production, so the version is checked before the environment is read. | §4 | resolved | `src/runtime/version.ts`, `src/runtime/version.test.ts` |
| 37 | Access-service outage | The gateway fails closed either way but **answers** differently. An explicit `{"allow": false}` is a denial: `403 workspace_forbidden`, counted as `access_denied`. A service that could not be asked, or an unreadable answer, is **service unavailability**: `503 access_unavailable` with `retry-after`, counted on `gateway_access_unavailable_total`. Previously both got the same refusal, which hid outages: operators could not tell a failing service from a denying policy, and the denial metric counted outages. | — | resolved | `src/domains/workspace-access/decision.ts`, `src/app/dispatcher.ts`, `test/contract/endpoints.test.ts` |
| 38 | Bearer token type | A bearer token must be an **access token**. The gateway used to accept id tokens too, since it checked only signature, issuer, audience, expiry and subject, and many providers issue both token kinds for the same client and audience. An id token passes through the browser (history, logs, referrers), so accepting it hands a browser credential to every bearer route. The browser flow always requests a nonce, so this client's id tokens always carry a `nonce` claim and access tokens never do: a bearer token with a nonce is refused. A provider with a token-type claim names it in `GATEWAY_OIDC_REQUIRED_TOKEN_CLAIMS`. The nonce check is on unless the deployment disables it. | — | resolved | `src/domains/authentication/oidc.ts`, `test/integration/oidc.test.ts`, `test/contract/endpoints.test.ts` |
| 39 | Request budgets | The three budgets (deployment, caller across routes, caller on the route) are counted **concurrently**. They are independent, so there is no reason to wait for one before the next, and the shared state is asked once instead of three times; capacity measurements attribute shared-state cost to round trips, and this is on every request's path. The reported refusal is the first in spec order, and **every budget is counted** even when one refuses, because the request was made. Pipeline order is unchanged: budgets are counted before authentication, so a flood stops before reaching the session store. | — | resolved | `src/app/limits.ts`, `src/app/limits.test.ts`, `test/integration/redis-round-trips.test.ts` |
| 40 | Identity signature key | In production the identity signature is **asymmetric**: the gateway holds the deployment's private key and upstreams hold the **public** key, so a verifying upstream cannot mint an identity. The symmetric format gave every upstream the signing secret, making the network, not the key, the trust boundary: any upstream that could reach the gateway could forge any subject. The key is P-256 and the signature `ES256`, a JWS verifiable with a standard library. Production refuses to start without the key: a setting that looks active but is not is a security hole. The format version is `v5`, so symmetric signatures never verify with the public key and vice versa. | §7.4 | resolved | `src/domains/forwarding/identity.ts`, `scripts/cli/identity-key.ts`, `test/contract/identity-signature.test.ts` |
| 41 | In-flight access-service calls | In-flight calls are **shared**: a burst for the same decision asks the service once. The decision cache empties whenever its short lifetime (five seconds by default) ends, so a burst at that boundary used to ask the service once per request. The access service is not a cache warmed once, and a stampede on it is a deployment outage. Every waiter receives the call's decision, and the call is released when it ends. | — | resolved | `src/domains/workspace-access/client.ts`, `src/domains/workspace-access/workspace-access.test.ts` |
| 42 | Path rewrite | A route may declare the path its upstream receives. Previously the route prefix was part of the forwarded path, so every upstream mounted elsewhere had to know the gateway's URL shape. A rewrite is a list of segments: route placeholders take the caller's values, and `{rest}` is the path after the matched prefix. A route without one forwards the request path, so deployments that declare none are unchanged. Values are as the caller sent them, so path encoding is untouched, and the identity signature covers the path the upstream receives. | — | resolved | `src/domains/routing/match.ts`, `src/domains/configuration/schema.ts`, `test/contract/rewrite.test.ts` |
| 43 | Request trace | The gateway writes its own W3C `traceparent` to the upstream. The caller's header is not forwarded as is, since a malformed one would confuse the upstream's collector; the gateway's span is new, so the upstream span is its child and the caller's trace continues. The trace id is logged next to the request id, so one search finds both halves of a request. Upstream latency is measured separately as `gateway_upstream_duration_seconds`: from the request leaving the gateway to the final response headers. It excludes authentication, limits and the access service, which gateway latency includes. | — | resolved | `src/domains/forwarding/trace.ts`, `src/domains/proxying/exchange.ts`, `test/contract/trace.test.ts` |
| 44 | Route upstreams | A route may name several upstreams, tried in list order. The next is tried when the **connection** to one fails, and only if the request may be resent: a state-changing request may not be sent twice, and a request with a body cannot be replayed because its bytes are already on the way to the first upstream. The response budget covers the whole exchange, so a list never lengthens a route's timeout. A WebSocket handshake goes to the first upstream, since it may not be sent twice. There is no health check: the list order is the file order, so route behaviour depends on nothing else. | — | resolved | `src/domains/proxying/exchange.ts`, `src/domains/configuration/schema.ts`, `test/contract/upstreams.test.ts` |
| 45 | Access-service protocol | The protocol is **published**: request, answer, statuses and meanings are in spec §6.1, and a **conformance suite** any implementation can run checks it (`test/support/access-conformance.ts`). The service is a deployment dependency, not part of the gateway, so a deployment that writes its own needs a way to prove it speaks the protocol; an uncheckable contract drifts. A **reference implementation** ships with the project (`services/access-service.ts`): it applies a policy file, runs in production, and the suite runs against it, so protocol and reference cannot drift either. It is not a fixture: fixtures carry accounts with known passwords and refuse to run in production, while the reference carries the operator's policy. | §6.1 | resolved | `docs/gateway/spec.md` §6.1, `test/support/access-conformance.ts`, `services/access-service.ts` |
| 46 | Running policy | The gateway logs the **policy it is running** once per generation: one line for the configuration, one per route, and one warning per permissive setting. A route's effective policy is spread over a JSON route table and dozens of environment variables, and an operator who must read both to discover an unauthenticated route will not find it. The warnings are not errors: a deployment may want an unauthenticated route, or one that passes the caller's credential upstream. They flag settings that look active but nobody may have read, which beats a silent default. The list is deliberately short, because a warning raised for everything is ignored. | §12.2 | resolved | `src/domains/configuration/describe.ts`, `src/runtime/policy-log.ts`, `src/runtime/policy-log.test.ts` |
| 47 | Unresponsive route upstreams | An attempt to an upstream that has another behind it is abandoned after `upstreamAttemptMs` (`GATEWAY_UPSTREAM_ATTEMPT_TIMEOUT_MS`, 2 s by default), and the next upstream is tried. Without it, an upstream that accepts the connection and never answers consumes the whole route budget (which covers the **whole** exchange), and the upstreams behind it are never reached: failover only worked when the port was closed. The attempt budget applies only to requests that may be resent, and never to the last upstream, which has no successor. The response budget still bounds the whole exchange, so a list never makes a route slower. The runtime cannot distinguish a connection never established from a slow upstream, so the attempt budget answers an imprecise question, and is applied only where a second request is harmless. | §11.4 | resolved | `src/domains/proxying/exchange.ts`, `test/contract/upstreams.test.ts` |
| 48 | Replayable body | A body is held in memory when its announced length fits `replayMaxBytes` (`GATEWAY_REPLAY_MAX_BYTES`, 64 KiB by default), so the request can go to a second upstream if the first fails. Previously a request with a body was never resent, whatever the method, so failover was useless for body-carrying traffic, which is most of an API. Only a body with an announced length that fits is read into memory, so memory is bounded by the limit, not by the client; other bodies are streamed and sent once, as before. Bodies are held only when the route names **several** upstreams: a single-upstream route has nothing to fail over to, and streaming preserves the upstream's early answer (spec §11.2). A state-changing request is never resent, whatever the body: the method decides, and only idempotent methods may be resent. | §11.4 | resolved | `src/domains/proxying/exchange.ts`, `src/domains/proxying/exchange.test.ts`, `test/contract/upstreams.test.ts` |
| 49 | Route methods | A route may name the methods it accepts. Between two routes matching the same host and path, the one naming the request's method wins, and a route naming no method is the fallback. Routes naming different methods are not ambiguous, so a `GET` and a `POST` on one path may reach different upstreams; routes naming the same methods are still refused. The rule is deliberately simple: matching on headers or query would let a caller-chosen value decide the route, and such a table's ambiguity cannot be checked at load time. | §3.3 | resolved | `src/domains/routing/match.ts`, `src/domains/routing/routing.test.ts`, `test/contract/methods.test.ts` |
| 50 | Access-service outage grace | An access-service outage took the whole deployment down: every request needing a decision got `503 access_unavailable`, and held decisions last only five seconds. A route may ask for a **grace** (`accessStaleGraceMs`, `GATEWAY_ACCESS_STALE_GRACE_MS`, default `0`) during which the service's last decision is served after it becomes unreachable. The grace is **off by default**, because an outage must be visible. A stale decision is served only when it **allows** the caller: serving a stale denial would hide the outage from the operator while refusing the caller exactly as failing closed does. A decision requested **fresh** is never stale, so revalidating an open connection still closes it after a revocation even during an outage. The grace delays revocation; the decision lifetime is the other knob of that delay. | §6.2 | resolved | `src/domains/workspace-access/client.ts`, `src/domains/workspace-access/workspace-access.test.ts`, `test/contract/access.test.ts` |
| 51 | Routes without a workspace | The access service could only be asked about a **workspace**, so a deployment without workspaces had to invent one, and the service had to understand the fiction. A route may now request a check with `accessCheck`; the service request then carries subject, route and roles, but no workspace. The protocol's `workspaceId` became optional, the reference implementation decides from its policy file's `routes` when none is named, and the conformance suite covers such requests. A check requires an authentication mode other than `none`: the gateway asks about callers it authenticated, and a check that could never run is a setting that looks active but is not. | §6.3 | resolved | `src/app/dispatcher.ts`, `src/domains/workspace-access/client.ts`, `services/access-service.ts`, `test/support/access-conformance.ts`, `test/contract/access.test.ts` |
| 52 | Body of a request never resent | The body of a request that may not be sent twice is **not held in memory**. It used to be: holding was decided when bodies were never resent, and the method condition was added later. So a `POST` body on a multi-upstream route was held for nothing, costing memory and delaying the upstream until the whole body arrived, which lost the early answer. The memory condition is now the full replay condition: several upstreams, an idempotent method, and a body within the limit. | §11.4 | resolved | `src/domains/proxying/exchange.ts`, `src/domains/proxying/exchange.test.ts` |
| 53 | Release compatibility | The gateway is on every request's path, and deployments write their own access services and upstreams against it. The contracts they depend on (gateway behaviour, access-service protocol, identity signature format, route-table format, variable and metric names) are now **versioned promises** (spec §16): a `MINOR` release extends them and never changes them; a `MAJOR` release changes them and says how to migrate. The symmetric identity signature (`v4`) was the first deprecation: production already required a private key, the gateway warned when signing symmetrically, and the format was to be removed in the first non-`0.x` release. Everything else (code organization, function names, log wording) is an implementation detail, and depending on it is unsupported. | §16.1, §16 | resolved | `docs/gateway/spec.md` §16, `src/runtime/composition.ts`, `src/domains/forwarding/identity.ts` |
| 54 | Upstream health | Failover only reached the second upstream when a request could be **resent**, so the most important traffic (an API's `POST`) had none: the request burned the route budget and never reached the second upstream. The rule that a state-changing request is never sent twice stays; it is what keeps one request from creating two workspaces. Instead, the gateway remembers recently failed upstreams and **moves them to the end of the list**, so the next request goes to one that answered recently. The breaker is **passive**: it learns from observed failures and never probes, because a probe is its own request needing an endpoint, timeout and interval, each a setting that looks active but is not. State is **per process**: a failure counter is not worth a round trip on every request, and a replica that missed the failure pays the route budget as it did before the breaker. Non-skipped upstreams come first, and file order is kept within each group, so list order still reflects the upstreams' order. | — | resolved | `src/domains/proxying/breaker.ts`, `src/domains/proxying/breaker.test.ts`, `test/contract/upstream-breaker.test.ts` |
| 55 | Revoking a caller's sessions | Sessions could only be ended one at a time or all at once for the whole deployment, so a compromised account meant hand-editing server state or logging everyone out. The session store now **indexes sessions by subject**, and revoking all of one subject's sessions is one operation. Revocation is a **script**, not a gateway endpoint: an administrative request the gateway answers is one an attacker can reach, and the gateway's admin surface decides who reaches the applications. The subject is hashed in the Redis index, because it comes from the identity provider and Redis keys are read by operators. Both backends hold the same index, and the conformance suite proves they behave alike. | — | resolved | `src/domains/authentication/adapters/redis-sessions.ts`, `src/domains/authentication/adapters/postgres-sessions.ts`, `scripts/cli/sessions.ts`, `test/support/shared-state-conformance.ts` |
| 56 | Cookies the gateway reads | The cookie parser was more permissive than the renderer: pairs without a name and names the standard forbids were read, then dropped on forwarding. Now the gateway reads **what it forwards**: a nameless pair is not a cookie, a name with a control character is not a name, and control characters are stripped from values.
