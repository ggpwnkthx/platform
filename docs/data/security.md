# Security

The data service's security model and its item-by-item review, with the findings still open.

The rules the service obeys are [Specification](spec.md) §2.3 (invariants) and §6.4 (row
isolation); this page reviews them and everything around them.

> [!IMPORTANT]
> **Review status:** the service is published as `1.0.0`, a pre-production release that has never
> run outside its own harness. It has no production history, no external users, and no audit not
> written by the code's author. Every "proved" below means "a check in this repository passes",
> nothing more.

The next version, `1.0.0`, is a release candidate: repository gates are green, and the two outside
gates (a deployment with a real studio and tenant, and a review by someone other than the author)
are listed in [Release readiness](release.md). The open findings below are the ones `1.0.0` doesn't
close; they are open on purpose and written down with their plan.

## Model

| Surface | Protection |
| --- | --- |
| Caller identity | A detached JWS from the gateway, verified with `ES256` and the gateway's **public** key. The route's binding pins the version, algorithm and header type, and the payload is rebuilt from the request: the transmitted payload never feeds the decision. A backend that verifies an identity cannot mint one. The legacy symmetric format is refused by default. |
| Request route | The deployment's bindings, matched on host and path; ambiguity is refused at load time. The path's workspace must equal the signature's. |
| Caller capabilities | The access service's access context: validated, fresh for every mutation, never cached by default. A missing, expired or malformed context is a refusal. |
| Rows | PostgreSQL row-level security, with the scope set on the transaction, so a pooled connection never carries another request's scope. |
| Fields | The statement builds a read's projection: a value the caller may not see never leaves the database. |
| Writes | One complete policy authorizes a write, and the row is checked before and after the change. |
| Statements | Every value is bound; every identifier comes from the manifest, which is validated as a whole. |
| History | The audit is append-only for the API role and holds field names, never values. |
| Image | Non-`root` user, no shell, no build tools, base image pinned by digest. |

## Review

| # | What was reviewed | Result | Where |
| --- | --- | --- | --- |
| 1 | **Identity verification.** The signature is a detached JWS: the payload is rebuilt from the method, path, query, host and header identity, and the signature is checked against it. Signature version, algorithm and header type come from the route's binding, the header's payload segment must be empty, and the key is the gateway's public key, never the session secret or the gateway's private key. | No finding | `src/domains/gateway-context/verify.ts`, `src/runtime/identity-keys.ts` |
| 1b | **The identity subject is read as is.** The `1.0.0` gateway writes the caller's subject without rewriting it, and access service token subjects are UUIDs. The backend rebuilds the signed bytes from the header bytes without trimming or normalizing the subject, so a subject other than the one the gateway wrote fails signature verification instead of being rebuilt into the original. | Fixed | `src/domains/gateway-context/index.ts`, `test/unit/gateway-context.test.ts` |
| 2 | **Verification fuzzing.** A random signature, a signature with one character changed, a header with another algorithm or type, a signature carrying its payload and a truncated signature are all refused, and verification never throws. The check runs in CI. | Fixed | `test/unit/fuzz.test.ts` |
| 3 | **The deployment, not the caller, chooses the signature version.** A route's binding names the version, algorithm and key file, and verification uses exactly those: a `v5` route refuses `v4`, a legacy route refuses a public key as its secret, and nothing falls back after a refused signature. Version, algorithm and key are never read from request headers. | No finding | `src/domains/gateway-context/bindings.ts`, `src/domains/gateway-context/index.ts` |
| 3b | **Legacy identity format.** The symmetric `v4` format is a signing-capable gateway secret, so a deployment holding it can mint identities. The service refuses it by default; a deployment that still needs it declares `DATA_LEGACY_IDENTITY`, and the format is removed in `2.0.0`. | Fixed | `src/domains/gateway-context/bindings.ts`, `src/runtime/config.ts` |
| 4 | **Request route.** The host is compared exactly, the pattern must match exactly one binding, and a path carrying an encoded separator, a backslash or a dot is not a workspace. | No finding | `src/domains/gateway-context/bindings.ts` |
| 5 | **Request workspace.** The path's workspace must equal the signature's; a header naming another workspace is refused. | No finding | `src/domains/gateway-context/index.ts` |
| 6 | **Access service context.** The context is validated before use and its deadline is rechecked just before commit. The context cache is off by default, so a revoked grant is visible on the next request. An access service that doesn't answer yields `503`, never a permission. | No finding | `src/domains/authorization/access-context.ts`, `src/domains/authorization/adapters/access-context.ts` |
| 7 | **Row isolation.** Business tables have forced PostgreSQL row-level security, so a table's owner is subject to it. The scope is set with `set_config(…, true)`, local to the transaction, and the database itself refuses a statement that forgets it. The API role may not alter the schema, update the audit or read deliveries. | No finding | `migrations/0004_isolation.sql`, `src/platform/postgres/scoped.ts` |
| 8 | **Workspace registry.** The workspace is read before the principal's context exists, by a reader limited to five columns of one table (ID, tenant, state, slug, name) that can only look up a workspace by exact ID. | No finding | `src/platform/postgres/adapters.ts` |
| 9 | **Read projection.** The statement assembles a row's payload, adding a field only when a policy that matched the row grants it, so a hidden value never leaves the database. The write path builds the same projection: the statement that locks the row computes the read-policy flags, so a record's validator is the same whether it was read or written. | No finding | `src/domains/records/service.ts` |
| 10 | **Two evaluations of a predicate.** Reads compile a predicate to SQL; writes evaluate it in memory over the locked row. The two must agree and didn't: in-memory evaluation used one comparison rule for every value, so numeric-looking text compared as a number and strings compared by UTF-16 code units. Comparison now follows the field's type, and the check's predicates are generated rather than hand-written. | Fixed | `src/domains/authorization/filter/compile.ts`, `src/domains/authorization/filter/evaluate.ts`, `test/integration/filter.property.test.ts` |
| 10b | **The database evaluates a write's predicate.** The write statement carries the policy predicates, compiled by the query compiler, and the post-change row is passed to the database as a CTE of bound parameters. In-memory evaluation remains the check's oracle, and the generated check compares both answers on predicates not written by hand. | Fixed | `src/domains/records/write-guard.ts`, `test/integration/write-guard.test.ts` |
| 10c | **The database evaluates a read's predicate.** The statement that locks a written row computes the read-policy flags, and the record's representation is built from them; the service no longer evaluates policy predicates in memory. The write path's in-memory evaluation remains the oracle, and the database decides. | Fixed | `src/domains/records/service.ts` |
| 11 | **SQL injection.** Every value is bound and every identifier comes from the manifest, whose names are pattern-validated. Fuzzing writes random filters and JSON and checks that no caller value reaches a statement as text and no caller identifier reaches it at all. | Fixed | `src/domains/authorization/filter/parse.ts`, `src/domains/authorization/filter/compile.ts`, `test/unit/fuzz.test.ts` |
| 12 | **Writing a JSON field.** A JSON list was bound as a database list literal, and the server refused the statement. JSON values are now bound as text. | Fixed | `src/domains/authorization/filter/parse.ts` |
| 13 | **Write authorization.** One complete policy authorizes a write; predicates and fields of two policies are never mixed, and a write no single policy allows stays refused. An update checks the row before and after the change. | No finding | `src/domains/authorization/rules.ts` |
| 14 | **Write relations.** A reference must be readable by the caller in the same tenant and workspace; an unreadable reference is refused with a generic error that never reveals whether the target exists elsewhere. | No finding | `src/domains/records/service.ts` |
| 15 | **Write concurrency.** A write needs the record's validator, and two writes with the same validator get one success and one refusal. A creation needs an idempotency key; replaying a key returns the first receipt. Claiming a key waits for the transaction holding it, bounded by a lock timeout. | No finding | `src/domains/records/service.ts`, `src/domains/records/canonical.ts` |
| 16 | **Page cursors.** Cursors are signed and bind the principal, tenant, workspace, collection, route, query, schema version, policy bundle version and caller permissions. Another caller's cursor, another query's cursor, and a cursor whose caller's permissions changed are all refused. | No finding | `src/domains/records/canonical.ts` |
| 17 | **Mutation atomicity.** Record, audit entry, event and receipt commit in one transaction, and the check injects a failure at every stage. | No finding | `src/domains/records/service.ts`, `test/integration/transactions.test.ts` |
| 18 | **Audit.** The API role may insert and read the audit but not update it. The log holds mutation identifiers and changed field names, never values. | No finding | `migrations/0002_platform.sql`, `migrations/0004_isolation.sql` |
| 19 | **Worker authority.** The worker has its own principal and route and asks the access service for its own fresh context; the originating user's headers are never credentials. Event chain depth is bounded. | No finding | `src/runtime/worker.ts` |
| 20 | **Event delivery.** Delivery is at-least-once, leases recover, and subscribers are registered by deployment code, never by a caller. | No finding | `src/runtime/subscribers.ts`, `src/platform/postgres/adapters.ts` |
| 21 | **Workspace catalog.** Registration never creates a table or names one the deployment doesn't declare for it. Bundle publication is an operator command, never a route, so the service holds no authority that bypasses the access service. | No finding | `src/domains/catalog/index.ts`, `scripts/cli/policy.ts` |
| 22 | **Work bounds.** Body size, in-flight requests, response size, filter depth and leaves, page size, group count and statement deadline are all bounded, and the authorization deadline is checked before commit. | No finding | `src/runtime/config.ts`, `src/domains/records/types.ts` |
| 23 | **Secrets.** The identity key is the gateway's public key: a compromised backend cannot sign an identity and never holds the gateway's private key or session secret. The legacy format, which derives the identity key from the gateway's session secret, is refused by default and removed in `2.0.0`. Secrets are read from files and never appear in the image or the log; the logger redacts fields known to carry one. | No finding | `src/observability/logger.ts`, `src/runtime/identity-keys.ts` |
| 24 | **Metrics.** The metrics endpoint answers nothing without its token, and `404` when the deployment has none. | No finding | `src/app/app.ts` |
| 25 | **Image.** Runs as non-`root`, with no shell and no build tools. The base image is pinned by digest, and CI builds and starts the image. | No finding | `Dockerfile`, `.github/workflows/ci.yml` |
| 26 | **Dependencies.** A CI step audits dependencies and fails the build on a known vulnerability. | Fixed | `.github/workflows/ci.yml` |
| 27 | **Metrics token comparison.** The token was compared with `!==`, so response time depended on the length of the common prefix. Both values are now hashed before comparison, and the secret's length never leaks. | Fixed | `src/app/secrets.ts` |
| 28 | **Database failures were internal errors.** An ungranted lock, a violated constraint and a statement over budget all answered `500 INTERNAL_ERROR`, so the codes the contract publishes for them were never produced. One table in the platform layer now maps SQLSTATE to contract codes, and database failures answer with those codes. | Fixed | `src/platform/postgres/errors.ts` |
| 29 | **A cursor refusal was an internal error.** Cursor refusal was its own class and never caught, so a tampered cursor answered `500 INTERNAL_ERROR` instead of the contract's `400 INVALID_CURSOR`. It is now a `ServiceError`; the refusal reason is the error's cause, not its message, and the response is the code's safe summary. | Fixed | `src/domains/records/canonical.ts` |
| 30 | **A failed statement took its pool connection with it.** A failed statement marked the transaction broken, and a broken connection was neither returned nor destroyed, so it leaked. Twenty failing writes exhausted the API pool, after which every request answered `503`. A failed statement no longer breaks a connection, and a broken connection is destroyed rather than returned. | Fixed | `src/platform/postgres/scoped.ts` |
| 31 | **The response size budget was checked after the response was built.** The contract's four mebibytes were checked once the page and expansions were in memory, bounding bytes sent rather than memory held. Relation expansion used one statement per root row, so a response could hold a thousand 200 KB related rows before refusal. The budget is now spent while building, expansion reads in chunks sized to the rows, and a page's relation is read with one statement, not one per row. | Fixed | `src/domains/records/budget.ts`, `src/domains/records/service.ts` |
| 32 | **The context cache was unbounded.** It was a map with no bound and no sweep; an entry left only when its key was requested again. The cache mitigates access service availability, and an unbounded mitigation is a leak. It is now bounded: spent entries leave, and the least recently used entry is evicted when full. | Fixed | `src/domains/authorization/index.ts` |
| 33 | **No per-tenant bound.** The listener's bound is the machine's, so a tenant sending more than others took their share, and the listener's `503 OVERLOADED` told the caller the service was broken rather than that it was sending too much. A per-tenant bound now applies once the request's tenant is known and answers `429 TOO_MANY_REQUESTS` with `Retry-After`. It defaults to the whole process's share; a multi-tenant deployment declares each tenant's share. | Fixed | `src/runtime/limits.ts` |
| 34 | **The suites might have no power.** The code's author wrote every check here, and a check that agrees with the code because it shares its assumptions proves nothing. The mutation gate breaks the code on purpose (protected header type, cursor expiry, cursor scope, row fields, write predicates, cache bound, pool connection) and checks that the suites notice. It found five unproven behaviours, and suites proving them were written. | Fixed | `scripts/gates/mutation.ts` |
| 35 | **Version history holds record values.** The audit holds mutation identifiers and changed field names, never values; version images are a separate surface and the first in the service to hold business values. They are read under the deployment's policies (the database evaluates read-policy predicates over every version image, as it does over the record), and a rollback is a write the same policies authorize. A version the policies hide is not found, and a forbidden rollback is refused: history is no path around authorization. The change statement writes the images; the API role may not update or delete them, and history retention belongs to the maintenance role. | No finding | `migrations/0008_record_versions.sql`, `src/domains/records/service.ts`, `src/domains/records/write-guard.ts` |

## Open findings

| # | Finding | Severity | Plan |
| --- | --- | --- | --- |
| 1 | **The predicate is evaluated twice.** Reads compile a predicate to SQL; writes evaluate it in memory over the locked row. One rule lived in two places and diverged three times before comparison followed the field's type. A generated check keeps them together by comparing both answers on predicates not written by hand. | Medium | **Closed.** The write statement carries the policy predicates and receives the post-change row as a CTE of bound parameters, so a write is checked against the row it produces. In-memory evaluation remains the oracle, and the generated guard check compares both answers. |
| 2 | **Service availability is the access service's availability.** The cache defaults to zero, so the context is requested on every call: a revoked grant is visible on the next request, and when the access service is down every platform call answers `503`. | Medium | The cache is configurable, bounded by the earlier of the access service's announced validity and the local lifetime. A deployment preferring availability over instant revocation sets `DATA_CONTEXT_CACHE_TTL_MS` and must declare the resulting revocation bound (cache lifetime plus running request duration). **The reference deployment declares it:** no cache by default, so revocation is bounded by the request duration (see [Capacity](capacity.md)). |
| 3 | **Write-path timestamp resolution is the millisecond.** The database driver reads timestamps at millisecond resolution while statements compare at microsecond resolution, so a row with a sub-millisecond fraction compares differently on the write and read paths. The API writes timestamps normalized to the millisecond, so service rows never hold one; this concerns rows written directly to the database. | Low | The same holds for a JSON field holding JSON `null`: the driver reads it as null and the statement doesn't. Both are outside the service contract, which says tables are written through the API; a row written otherwise means the deployment broke the migration contract. |
| 4 | **The service has never run outside its own harness.** No production history, no external users, no review not written by the code's author. The test suites map every specification requirement to a repository check, but an author's check is not an assurance. | Medium | `1.0.0` is published and says so: release notes and README mark it pre-production, and the suites say "checked", not "proved". The first deployment with a real studio and tenant is the review the harness can't replace. **The mutation gate is the part of the plan the repository can hold:** it doesn't replace an outside review, but answers what a machine can, namely whether the suite notices when the code is broken on purpose. It found five unproven behaviours. |
| 5 | **Suites and code share assumptions.** A suite by the code's author agrees with the code when the code is wrong in a way the author imagines. The mutation gate answers that risk only partly: it covers the mutations someone thought of, and a surviving mutation is a behaviour nothing in the repository proves. | Medium | The gate is a CI step and grows with the code: every behaviour the security review names has a mutation that breaks it, and the mutation names the suite that catches it. The repository's gate covers fourteen trust-boundary mutations; an outside review remains the gate the repository can't hold. |
