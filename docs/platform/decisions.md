# Decisions

Decisions about the shape of the repository, taken when the three service repositories were merged. Contract decisions live with each service: [gateway](../gateway/decisions.md), [access service](../access/decisions.md), [data service](../data/decisions.md). Those pages share one format: contract decisions in a table whose **Stated in** column names the spec section, followed by implementation decisions.

| # | Decision | Evidence | Status |
| --- | --- | --- | --- |
| 1 | The three services are three workspaces of one repository, not one service. | They are separate deployments with separate secrets, databases and contracts. Shared source would couple their builds and break single-service deployments. Their boundary is their specs' boundary, and the merge keeps it. | resolved |
| 2 | No workspace imports another workspace's source. | Services talk over HTTP under their specs' contracts. Each workspace's architecture check rejects cross-workspace imports (`packages/gateway/scripts/gates/architecture.ts`, `packages/access/scripts/gates/architecture.ts`, `packages/data/scripts/gates/architecture.ts`), and the compatibility suite runs the acceptance scenario through all three services. | resolved |
| 3 | All three images build with the repository root as context. | Dependencies come from the root `bun install`, and the root `bun.lock` covers all three. An image built from a workspace directory would install a tree the others don't share, which the root lockfile would reject. | resolved |
| 4 | There is one version: the platform's. | The retired repositories' version lines are not continued. The repository, tag, three images, three binaries **and** the three specs' status share one version; a spec naming another release describes behavior the code doesn't have. `scripts/version.ts` checks they agree. | resolved |
| 5 | Images and environment prefixes are renamed. | Image names and env prefixes are deployment coordinates, so renaming them is a migration, recorded in the changelog. The old prefixes came from retired repository names; a variable with a retired name is read by no service, and a deployment that sets it only believes it configured something. | resolved |
| 6 | The data service's published client keeps its name. | `@data-backend/client` (`packages/data/packages/client/package.json`) is installed by consumers. Renaming it breaks them, and merging source is no reason to. | resolved |
| 7 | The compatibility baseline is a revision of this repository. | The suite's references used to be the gateway and access service in two other repositories at two commits. They are workspaces here now, and running this repository's code at a revision proves more than cloning a copy. Environment overrides still name a published revision, and a run with one tests a candidate. Manifest: `compatibility.json`. | resolved |
| 8 | One tagger, one CI workflow, one image workflow, one binary workflow. | There were three of each, nearly identical and drifting. The three services keep their existing jobs, and the jobs are the same for each: a gate present for one service and missing for another was forgotten. See `scripts/tag.ts`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `.github/workflows/release-binaries.yml`. | resolved |
| 9 | All documentation is one tree at the repository root. | Contracts are normative and are read alongside the shared docs. They used to live apart (platform docs at the root, each contract in its workspace), so readers of one had to find the other. Now `docs/platform/` holds shared docs and `docs/gateway/`, `docs/access/`, `docs/data/` hold the contracts. The code boundary did not move: no workspace imports another's source. | resolved |
| 10 | Platform tools are declared at the root; a service's dependencies are declared in its workspace. | The compiler, linter, formatter and dead-code checker serve all three at one version (root `package.json`). A service declares what it uses, and a workspace that doesn't use a dependency doesn't carry it. | resolved |
| 11 | Specs name services by role, and so does the platform. | A contract must name the service it describes, and a retired repository's name names nothing. The platform, workspaces, images, environment and docs call the three the gateway, the access service and the data service, because the role is what the repository is about. | resolved |
| 12 | The platform never names the retired repositories, and a check enforces it. | The old repositories are gone: clones fail, their releases are unreachable, and docs telling an operator to clone one lead nowhere. The platform names one repository, one set of images and one release line. `scripts/check-repositories.ts` fails the build when a file names any other repository. It lists no retired names; it accepts only the platform's, because a list of dead ends names them again. No record of the old state is kept either: the merge plan and the three services' histories are gone, and the retired version lines are not continued. | resolved |
| 13 | Each service's vocabulary carries its role name. | The old names came from the retired repositories and now name nothing. The platform uses role names in workspaces, code, deployments and docs, and the vocabulary moves with them: metrics, identity headers, cookies, tables, shared-state namespaces and env prefixes. A dashboard watching a retired metric name sees nothing, and a deployment setting a retired variable configures nothing. | resolved |
| 14 | A vocabulary check rejects identifiers that don't carry their service's role name. | A service's env prefixes, metric names and reported name carry its role. An identifier with a retired name is read by nothing. `scripts/check-vocabulary.ts` lists no retired names; it accepts only the role names, because a list of dead ends would have to be maintained and would name them again (decision 12). | resolved |
| 15 | All three services answer probes the same way and publish an API description. | Deployments read every service's probes with the same code. Readiness uses the platform vocabulary (`ready`, `draining`, `not-ready`), and health carries the status, the service's role name and the release version. Each service publishes an API description so clients know its surface without reading source. `scripts/check-api.ts` holds each description against the registered routes: an undescribed route is unknown to clients, and a described but unserved endpoint is a broken promise. | resolved |
| 16 | A decision that changes a contract is recorded in the workspace's spec, its decisions table and the changelog, never only in code. | The spec is the contract, the decisions table names the spec section stating each decision, and the changelog is what release readers read. Code says what it does; the contract says what it promises. Platform decisions are in this table; contract decisions are in each workspace's table. | resolved |
