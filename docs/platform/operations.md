# The operations of the platform

The platform is three deployments. This document holds what is common to
the three of them. The environment, the probes, the alerts and the
runbooks of each service are in the documentation of its contract:

| Workspace | The operations |
| --- | --- |
| `packages/gateway/` | [docs/operations.md](../gateway/operations.md) |
| `packages/access/` | [docs/operations.md](../access/operations.md) |
| `packages/data/` | [docs/operations.md](../data/operations.md) |

## The three deployments

| Service | The image | The listener | The environment | The state it needs |
| --- | --- | --- | --- | --- |
| The gateway | `ghcr.io/ggpwnkthx/gateway` | `8080` | `GATEWAY_*` | A Redis server or a PostgreSQL server, for the sessions, the limits and the cached decisions. |
| The access service | `ghcr.io/ggpwnkthx/access` | `8081` | `ACCESS_*` | A PostgreSQL server for the five tables, and a Redis server for the codes of the logins. |
| The data service | `ghcr.io/ggpwnkthx/data` | `8082` | `DATA_*` | A PostgreSQL server for the rows of the business data. |

The gateway has a second process: the **control plane**, the
administrative surface of the deployment. It is the same image with
another command, it listens on `9090`, and it is never routed through
the gateway.

## The first deployment

The order of the steps of a deployment that starts from nothing. Every
command of the list is an operator command of the platform or of one of
its services, and the manual of each one is in the documentation of its
contract. The commands are the ones of the repository: a deployment that
runs the images runs the same commands in the same order.

### 1. The secrets

A secret is a file, never a value of the environment, whenever the
service can read it from a file. The keys of a development machine are
generated by the repository:

```bash
bun run scripts/dev-keys.ts
```

A deployment mounts the files of its secret manager and points the
variables of the services at them: `ACCESS_SIGNING_KEY_FILE`,
`DATA_CURSOR_KEY_FILE`, `DATA_ACCESS_CONTEXT_TOKEN_FILE` and so on. The
variables that a stack refuses to start without are in
[`.env.min`](../../.env.min) at the root of the repository.

### 2. The database and the roles

The roles of the separation of the data service are created once, with
the credentials of an administrator of the server:

```bash
bun run --cwd packages/data provision
```

### 3. The schema

The migrations are applied by the operator, with the credentials of the
owner of the schema, and never by the api:

```bash
bun run --cwd packages/data migrate
```

### 4. The workspace

The registry of the workspaces is written by the operator as well: the
workspace is the unit of access control, and the data service reads it
before the context of a principal exists.

```bash
bun run --cwd packages/data workspace create \
  --id 11111111-1111-4111-8111-111111111111 \
  --tenant 22222222-2222-4222-8222-222222222222 \
  --slug acme
```

### 5. The tenant, the principals and the grants

The access service holds them, and its administration is the only way
to create them: the calls are in
[the operations of the access service](../access/operations.md) §"The
first tenant", and the rehearsal of them is the suite of the cutover.

### 6. The route table

The gateway matches the requests with the route table: it is a file
(`GATEWAY_CONFIG`) or the shared state, where the control plane writes
the revisions of it. The shape of the table is in
[the specification of the gateway](../gateway/spec.md) §3, and the
configuration of a deployment is in `deploy/config/routes.json`.

### 7. The stack

```bash
docker compose --env-file .env.min \
  -f deploy/compose/production/platform.compose.yaml up -d
```

### 8. The check

```bash
curl -sS http://localhost:8080/healthz
curl -sS http://localhost:8081/healthz
curl -sS http://localhost:8082/healthz
```

A request that reaches the gateway and is answered by the data service
is the check that the three deployments talk to each other: the caller
is authenticated, the access service allows the workspace, and the data
service returns the row.

## The addresses

A deployment names the addresses of the other two in its environment,
and it names them as the urls of the services.

| What | Where the address is configured |
| --- | --- |
| The issuer of the access service | `GATEWAY_OIDC_ISSUER`, with the client and the redirect of the deployment |
| The access service | `GATEWAY_ACCESS_URL` |
| The upstream of the data service | The `upstream` of the route in the route table of the gateway |
| The access service of the data service | `DATA_ACCESS_URL` |
| The bindings of the gateway | `DATA_GATEWAY_BINDINGS_FILE` |

The gateway integrates with **any** conforming identity provider, access
service and upstream. The access service and the data service are the
ones that ship with the platform, not the only ones it can talk to.

## The probes

Every service answers two probes, and they are the same for the three:

| Endpoint | Behaviour |
| --- | --- |
| `GET /healthz` | Always `200`. It says that the process is alive. |
| `GET /readyz` | `200` when the service can serve a request, `503` otherwise. |

The readiness of the gateway needs the shared state: the sessions of the
callers have to be storable. The readiness of the access service needs
the database and the shared store. The readiness of the data service
needs the schema, the role of the connection and the access context of
the access service.

## The metrics

Every service exposes the metrics of Prometheus on `/metrics`. The
gateway and the access service guard the endpoint with a bearer token,
and the endpoint is absent without it. The data service reads the token
from a file.

The name of the metrics of each service is in the documentation of its
workspace.

## The secrets

A secret is a file, never a value of the environment, whenever the
service can read it from a file. The gateway, the access service and
the data service all accept a secret in a file next to the variable
that names it: `ACCESS_SIGNING_KEY_FILE`, `DATA_CURSOR_KEY_FILE`,
`DATA_ACCESS_CONTEXT_TOKEN_FILE`, and so on.

A deployment that runs the three of them mounts the secrets of its
secret manager and it points the files at them.

## The images

```bash
docker pull ghcr.io/ggpwnkthx/gateway:1.0.0
docker pull ghcr.io/ggpwnkthx/access:1.0.0
docker pull ghcr.io/ggpwnkthx/data:1.0.0
```

The images are built once per release, published with their provenance
and their SBOM, and every gate of the release runs against the **digest**
of that build. The digest is what a deployment pins.

## The rollback

The images of a release are published with the tag of the release and
with the version itself. A rollback is the deployment of the image of
the previous release:

```bash
docker pull ghcr.io/ggpwnkthx/gateway:<the version of the release to roll back to>
```

The schema of the data service is not rolled back with its image: the
migrations are applied by the operator command, and they are described
in [the migrations of the data service](../data/migrations.md).

## The platform as a whole

The three services are independent deployments, and they are versioned
together: a release of the platform carries the three images at the same
version. A deployment may run them at different versions, and the
compatibility suite proves which combinations work: see
[the compatibility of the platform](compatibility.md).
